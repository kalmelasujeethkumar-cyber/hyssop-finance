# HYSSOP FINANCE — Decisions

## Document Responsibility

- Owns: accepted technical decisions, `DEC-*` identifiers, reasons, alternatives, and impacts.
- Does not own: current status, open issues, test results, or locked product requirements.
- Referenced by: affected specifications, phase documents, and the traceability matrix.
- Change rule: record a decision only after the owning specification is updated or confirmed; a decision that weakens a locked requirement is a stop-and-ask condition.

Decisions are recorded so that future phases do not rely on conversational memory. A decision that conflicts with a locked requirement must stop and ask the user instead of being recorded as settled.

## Phase 03 authentication decisions

| ID | Decision | Status | Impact |
|---|---|---|---|
| DEC-064 | Hash Admin passwords with Argon2id at 19456 KiB memory, 2 iterations, and 1 lane, with the parameters read from validated environment configuration rather than hard-coded at the call site. | Accepted in Phase 03 | OWASP's Argon2id baseline. Memory cost dominates, so raising it later is a configuration change rather than a code change, and a deployment can be measured and tuned without a release. |
| DEC-065 | Deliver the pre-authentication CSRF secret as a short-lived, origin-bound, single-use token returned in the `GET /api/v1/auth/csrf` body **and** as a matching readable CSRF cookie, and require `login` to receive both, with the `X-CSRF-Token` header and the cookie value matching. | Accepted in Phase 03, contract mismatch corrected | `docs/07-SECURITY-RULES.md` already required a cookie/token pair; the first implementation issued only the body token, which satisfied neither the double-submit intent nor the origin binding the specification describes. A token alone cannot protect login, because a cross-site caller can send a custom header only through a preflight the trusted origin would answer. Requiring the pair is what makes the pre-authentication flow meaningful, and the token stays single-use, origin-bound, and short-lived. Recorded as `ISSUE-020`. |
| DEC-066 | Enforce the login rate limit in-process per API process, keyed on a salted hash of the client address, with the window and attempt count read from validated environment configuration. | Accepted in Phase 03 | The single-Admin demo needs brute-force resistance without new infrastructure, and the documented values live in configuration so a deployment can tighten them. The honest limit is per process: a multi-instance deployment multiplies the effective allowance by the instance count. A shared store is recorded in `ISSUES.md` as future work rather than pretended to be solved. |
| DEC-067 | Return `POST /api/v1/auth/logout` as HTTP 200 with the canonical success envelope carrying `{ revoked: boolean }`, rather than a bodyless 204. | Accepted in Phase 03, contract mismatch corrected | `docs/06-API-SPEC.md` requires the standard `data` property on every successful response, and the browser client rejects a bodyless success. `revoked` reports honestly whether a live session was actually revoked, and revocation failure is returned as an error so a failed sign-out can never be presented as successful. ## Phase 05 income decisions

| ID | Decision | Status | Impact |
|---|---|---|---|
| DEC-074 | `memberId` belongs in `CorrectableTransactionFields` and in the repository's `CORRECTABLE_FIELDS` allow-list, with `null` treated as a real correction rather than an absent field. | Accepted in Phase 05, production defect corrected | `docs/06-API-SPEC.md` permits editing "type-specific associations permitted by the transaction type", and `TransactionsService` implements exactly one such rule: a member contribution cannot be re-linked, while an offering or donation may name a member and `null` detaches one. The service computed `changes.memberId` correctly, but the repository filtered input through an allow-list that omitted `memberId`, so the computed change was discarded. The failure was silent and dishonest in two ways: a member-only correction was rejected as "changes nothing", and a member correction sent alongside an amount answered `200`, incremented the revision, and wrote an audit event whose `before` and `after` member were identical while the stored record kept the member the Admin believed they had removed. Adding the field makes the repository's allow-list match the service's rules, and the interface comment now records why an omitted field here is a data-loss defect rather than a harmless omission. Verified at the contract layer by two HTTP tests that assert the stored row and the audit `before`/`after` pair, not only the response body. Recorded as `ISSUE-026`. |
| DEC-076 | The browser derives a member contribution's month from the business date the Admin already entered, and sends it as `contributionPeriod`; it is not a second, separately editable control. | Accepted in Phase 05, production defect corrected | `docs/phases/PHASE-05-INCOME.md` requires "a member and contribution period for Member Contribution" and `docs/06-API-SPEC.md` shows `contributionPeriod: { year, month }` in the create body, so the browser must supply the month or the API correctly refuses the write. The month is *derived* rather than asked for because the business date already states which Asia/Kolkata day the money belongs to, and a second month control could contradict it: the Admin would be able to file a 28 September payment under August and be shown a contribution status for a month the transaction was never in. Deriving also keeps the period the Admin configured on the member intact, because the API opens the member-month with the configured or default expectation rather than resetting it. The alternative — a month and year control — was rejected for that contradiction risk, not for effort. The derivation is exact string slicing of the validated `YYYY-MM-DD` value, so it introduces no `Date`, no time zone, and no floating-point arithmetic. Recorded as `ISSUE-027`. |

The in-code comment claiming a deliberate `404` contradicted the code beneath it and was corrected to match. |

They are seeded by migration `20260929210000_app_setting_initial_keys`, and the destructive `reset()` truncated the same table and left the test database without them, so every later browser run failed against a database no real deployment would ever be in. The constant does not replace the migration, which still owns the seeded rows; it makes the set the test harness restores explicit, and `schema-invariants.db-spec.ts` now asserts against a real PostgreSQL database that the rows exist after a reset and are readable through the repository. | DEC-078 | Keep one `invalidateTransactionDependents(queryClient)` helper in the shared transaction layer that invalidates the transaction list, detail, audit, and receipt keys, the contribution-period summary, and the **member detail**, and call it from income create, transaction correction, and transaction void. ## Phase 06 expense decisions

| ID | Decision | Status | Impact |
|---|---|---|---|
| DEC-079 | The shared transaction service returns a single transaction through `toTransactionView()`, which dispatches on the stored type to the income or expense projection. The list route keeps `toTransactionSummary()`. | Accepted in Phase 06, production defect corrected | Income and expenses share one canonical `financial_transaction` record (`DEC-004`), so `GET /api/v1/transactions/:id`, the correction response, and the void response are reachable by an expense as well as by an income record. Those three responses previously used the income-shaped summary projection, so an expense read through them lost `category` and `hasReceipt` while `GET /api/v1/expenses` answered correctly — two routes describing the same stored row differently, which the state-honesty rule forbids (`ISSUE-032`). Dispatching by stored type rather than widening the summary keeps one place that decides what a full transaction view contains, and it means a future transaction type gets one branch rather than a second endpoint. The list keeps the narrower projection deliberately: every list row is satisfied without the extra join, and the shared list is used by the dashboard and reports that Phase 08 and Phase 09 still have to define, so widening it now would pre-empt their contract. |
| DEC-080 | The inline "Add a category" panel inside the expense record form is a `<fieldset>` with a `type="button"` action and an explicit Enter handler, never a `<form>` of its own. | Accepted in Phase 06, markup defect corrected | `docs/03-UI-UX-RULES.md` requires the record form to stay usable while a category is added inline, and HTML does not permit one form inside another: Chromium's parser discards a nested `<form>` and lets its closing tag close the outer form. A nested form also leaves one submit control owning submission for two independent operations, which is how the category panel could submit the record form (`ISSUE-033`). A `fieldset` is the correct grouping element for a set of related controls and has no form owner, so it can live inside the record form, be disabled and `aria-busy` while the category request is in flight, and still present one control that submits. Enter is handled explicitly because implicit submission belongs to the form, not to a nested panel, and leaving it to the browser would submit the record form from a field the Admin filled to name a category. |
| DEC-081 | The browser acceptance harness provisions the initial expense categories itself, idempotently, in `global-setup.ts`, instead of the API test database's `reset()` restoring them. | Accepted in Phase 06, harness defect corrected | `reset()` must leave `expense_category` empty so the category repository tests can create, rename, and deactivate categories without inheriting each other's rows; that is the isolation `expense-persistence.db-spec.ts` exists to protect. The browser suite, however, needs a real category set to have anything to select. `restoreInitialExpenseCategories()` resolves this without either side lying: it derives the set from the same canonical `INITIAL_EXPENSE_CATEGORIES` constant the seed uses, so the harness cannot drift from `REQ-EXP-001`, it reuses `skipDuplicates` and a reactivation pass so repeated runs are safe, and it verifies the resulting normalized-name count instead of trusting its own writes. Seeding inside `reset()` was tried and reverted because it made the repository suites share state (`ISSUE-034`). The trade-off is accepted: the harness provisions, and a database-suite change can no longer silently remove what a browser run depends on. |
| DEC-082 | An expense with no attached document is reported as `hasReceipt: false` and rendered as **Receipt Missing**, and Phase 06 ships no attach or upload control. | Accepted in Phase 06 | `REQ-DOC-003` requires the missing receipt to be visible, and `docs/phases/PHASE-06-EXPENSES.md` prohibits a temporary upload system because Phase 07 owns the reusable storage subsystem. The gap that creates is a visible one either way: either the screen offers a control that cannot succeed, which the phase document prohibits, or it states the fact in words and explains that attaching a document is not available yet, which is what the phase scope authorizes. `hasReceipt` is derived from the document association rather than stored on the transaction, so it cannot disagree with the documents that actually exist, and the HTTP suite proves both directions by attaching a document row and asserting the flag flips. |
| DEC-083 | A duplicate expense category is refused as `409 CONFLICT` carrying `details.field: 'name'`, and the browser shows the API's own message against the name input. | Accepted in Phase 06 | Uniqueness is case-insensitive and whitespace-insensitive, which is enforced by the database as well as the repository, so a race between two Admins cannot create a near-duplicate. The repository's existing convention is a `field` key inside `DomainError` details, and `ApiExceptionFilter` turns exactly that key into the documented `fields` issue while keeping every other internal detail out of the response. The browser then needs no new lookup: `fieldIssuesByName(error).name` already resolves a field-keyed issue to the input it belongs to, and an unknown field keeps its own name rather than being attached to the first input. The consequence for tests is recorded rather than hidden: the web unit suite passes against a stub that supplies its own text, so a journey must assert the API's wording, which is what exposed `ISSUE-035`. |

## Phase 07 documents decisions

| DEC-084 | Multipart error mapping lives in the global `ApiExceptionFilter`, not in a route-scoped filter, and it matches only the documented Multer codes. | Accepted in Phase 07, production defect corrected (`ISSUE-036`) | A route-scoped `@Catch()` filter in NestJS is not a handler for one error class: it intercepts every exception raised while that route is being served. Mounting it on the upload handler therefore rewrote the authentication and authorization failures raised upstream as `400 VALIDATION_FAILED`, so the browser could not tell "you are not allowed" from "your file was rejected". The mapping also matched any error carrying a `code` string, which is a property many unrelated errors have. Placing the mapping in the global filter, ordered after the `DomainError` and `HttpException` branches and before the unhandled branch, keeps every existing status honest and leaves the handler with no cross-cutting error logic at all. `describeMultipartError` recognises the documented Multer codes and returns `null` for anything else, so an unfamiliar error falls through to `500` instead of being relabelled. |
| DEC-085 | `FileInterceptor` uses `preservePath: true`, and the filename validator refuses any filename containing a path separator instead of sanitising it. | Accepted in Phase 07 | Multer's default behaviour strips directory information from the filename before the application sees it, so `../../etc/passwd.jpg` would arrive as `passwd.jpg`. That hides the traversal attempt from the one component positioned to refuse it and makes the test suite unable to exercise the case at all: the form-data client also basenames the filename, so a test could only assert the sanitised path and would never prove the refusal. Preserving the path means the validator sees what the client actually sent, and it refuses it. Sanitising was rejected rather than also offered: a receipt whose name the Admin believes is `September/bill.jpg` is not the file they chose, and quietly accepting a partial name would misreport what was stored. `assertUploadFilename` therefore refuses separators, and the storage layer additionally validates the key format it was given, so containment does not depend on the filename check alone. |
| DEC-086 | The database requires a non-empty `storage_key`; the 64-character lowercase hexadecimal format is enforced by the storage adapter as an invariant, not by a database CHECK constraint. | Accepted in Phase 07 | `docs/05-DATABASE-SPEC.md` specifies a non-empty storage key and does not specify a format constraint, and adding a CHECK that the specification does not own would create a second, competing authority. The format is nonetheless a real invariant, and it belongs in the adapter because the adapter is what turns a key into a path: a key that is not exactly 64 lowercase hexadecimal characters cannot be a key this system issued. That also keeps a production adapter free to change its key format without a migration, which is the whole point of the abstraction in `docs/02-ARCHITECTURE.md`. The consequence is recorded rather than hidden: the raw-constraint suite asserts a non-empty key is required and that an arbitrary non-hexadecimal non-empty string is accepted by the database, so the two layers cannot be confused for each other. |
| DEC-087 | The browser fetches document content through a server-supplied path into a blob URL, and revokes that URL on unmount. It never builds a path from an id. | Accepted in Phase 07 | `downloadPath` and `previewPath` are returned by the API as versioned relative paths, and the contract states that the browser must not infer them. Using them verbatim is what guarantees the browser cannot offer a control for a URL that does not exist, and it means a future change to the version prefix needs no browser change. The content is fetched rather than linked because the session is an HTTP-only cookie the request must carry with `credentials: 'include'`; a plain `<a href>` cannot guarantee that for a binary response and would surface as a `401` reported as a missing file. Fetching into a blob also makes revocation possible, which a new tab is not: every object URL this component creates is revoked on unmount, because a blob URL pins its bytes for the life of the document. |
| DEC-088 | The browser's upload size pre-check is advisory and states itself as such; the API's configured `UPLOAD_MAX_BYTES` is the only enforcement point. | Accepted in Phase 07 | A browser check that claimed to be the limit would be a second, divergent source of truth the moment an administrator changed `UPLOAD_MAX_BYTES`, and the interface would then reject files the API would have accepted, or accept files the API refuses. The pre-check exists only to spare a non-technical pastor a multi-megabyte round trip before being told no, it matches `DEFAULT_UPLOAD_MAX_BYTES` so the common case agrees, and its message says "larger than the 10 MB upload limit" rather than implying the browser decides. The API remains authoritative and the HTTP suite proves a genuinely oversized body is refused with `413` regardless of what the browser allowed. |
| DEC-089 | The browser uses the server-supplied `downloadPath` and `previewPath` verbatim rather than stripping a version prefix before passing them through the API client. | Accepted in Phase 07 | The paths the API returns already include the `/api/v1` prefix, while the API client prepends its own configured base URL. Passing a server path through the client would therefore produce `/api/v1/api/v1/...`, so the panel fetches these two paths directly and every other call goes through the client. The alternative — stripping the prefix to satisfy the client — would reintroduce exactly the client-side path inference the contract forbids, and would break the day the prefix changed. The consequence is that these two requests do not go through the session-expiry wrapper; they instead report the server's own error and are consistent with `docs/03-UI-UX-RULES.md`, which requires a failure to be shown rather than swallowed. |
| DEC-090 | A browser acceptance journey must narrow the list by search before asserting that a filter removed a specific row. | Accepted in Phase 07, test defect corrected (`ISSUE-039`) | `hyssop_finance_test` is deliberately not reset between runs, so the ledger grows with every run and a record this run created is not guaranteed to be on the first page. An assertion of "count 0" then passes for a record that is merely on page two, which means the assertion proves nothing while still looking strong. Narrowing by the run's unique text first makes the record known to be on screen before the filter is applied, so absence afterwards is real absence and reappearance is real. This is recorded as a rule for future journeys rather than fixed once: any journey that asserts a specific row's presence on an unfiltered list has the same defect. |
| DEC-091 | The expense record form carries no file input; receipts are attached from the transaction detail screen. | Accepted in Phase 07 | A document belongs to a transaction by id, so there is nothing to attach to before the expense exists. Offering the control in the create form would mean either buffering a file in the browser and uploading it after the record was created, which loses the file if the second request fails, or inventing an id before the record exists. Attaching from the detail screen keeps one operation, one request, and one honest state: the form states that the expense will be recorded with no receipt attached, and the receipt panel on the record is where a receipt is added. The browser tests now assert that the create form has no file input as a design consequence, rather than as a missing feature. |

| DEC-092 | Removal state is held per document id, so one receipt's reason, error, and idempotency key can never be applied to a different receipt. | Accepted in Phase 07 | `REQ-DOC-005` allows several documents on one transaction, which makes a single shared reason box a correctness problem rather than a layout one: the Admin types "uploaded by mistake" while looking at the first receipt, clicks **Remove receipt** on the second, and removes the wrong file with a reason they never wrote. A shared key is worse, because it deduplicates two different removals against each other. The panel therefore holds a `removals` record keyed by document id, minting the idempotency key on the first keystroke of an intent and reusing it for a retry, and clearing it only once the removal succeeds. One receipt behaves exactly as before, because a one-receipt transaction has only one key in the record |
| DEC-093 | A failed document content fetch is reported in the panel rather than swallowed. | Accepted in Phase 07 | The fetch catches errors so a failed open does not throw out of a click handler, but returning nothing leaves a visibly enabled control that does nothing, which is precisely the dead control `docs/phases/PHASE-07-DOCUMENTS.md` prohibits. The earlier justification — that the server's `410` is "already reflected in the list" — was wrong: the list reflects the state as of the last read, so a receipt whose storage became unavailable after that read would present an enabled button and no explanation. The panel now shows a banner and the click is retryable, which satisfies the state-honesty rule in `docs/03-UI-UX-RULES.md` |

| DEC-094 | Recent transactions order by `business_date DESC, created_at DESC, id DESC`. `occurred_at` is not used to order them. | Accepted in Phase 08 | `occurred_at` is derived as the start of the business day in both create paths, so it is identical for every row sharing a date and cannot break a tie; the third term was therefore `id DESC` on `gen_random_uuid()`, which orders same-day rows randomly and let a just-written entry fall outside a list that states it shows the ten most recent (`ISSUE-043`). `created_at` is the genuine recorded instant and is immutable under `HY_FIN_IMMUTABLE_TRANSACTION_FIELDS`, so it orders ties so the entry written last appears first, while `business_date` stays first because that is what "recent" means to a bookkeeper entering a back-dated receipt. `id` is retained solely for an exact `created_at` collision, so a reload still cannot reshuffle equal rows |
| DEC-095 | A period control that changes the selected range issues one dashboard request per selection change, and only a period the browser has not already fetched triggers a network request. | Accepted in Phase 08 | React Query caches each period under its own key, so a repeat selection is served from cache without a request. That is correct caching, not a dead control, but an assertion that every switch must hit the network would be asserting the opposite of the intended behaviour. The browser journeys therefore assert that a cold period sends its own `from`/`to` pair and that a cached period still renders the correct values, which proves the filter works rather than proving a request was made |
| DEC-096 | One row cap per report shape, shared by the screen and the export: a report that is not separately paged returns at most `REPORT_ROW_LIMIT` (1,000) rows and sets `rowsTruncated` when more exist; a paged report returns the requested page within `TRANSACTION_PAGE_SIZE_MAX` (100). CSV export asks the same projections for page 1 and is therefore never more complete than the screen. There is no separate, larger export cap and no "download everything" route. | Accepted in Phase 09 | `docs/06-API-SPEC.md` requires the same projections for the screen, CSV, and print, and `docs/phases/PHASE-09-REPORTS.md` prohibits a CSV that misrepresents the report, so an export with its own larger limit could contradict the visible report while still agreeing with the database. A single cap makes the truncation warning and the exported file describe the same bounded window, and `rowsTruncated` lets the screen name the remedy instead of silently showing part of a total. The Audit report is the one export that needs a bounded window in the request itself: the export route reads a period, so a whole-history audit or a one-sided window replaces the control with its reason rather than exporting something the Admin did not ask for |
| DEC-097 | The voided-visibility sentence on every report is read from `REPORT_EXCLUDES_VOIDED` in the contract, not written per screen. | Accepted in Phase 09 | `REQ-REPORT-001` and the state-honesty rule require the screen to say whether voided records are excluded or retained. A hand-written sentence per report could contradict the projection behind it, and the Audit report in particular would be the easiest to get wrong. Reading one constant means the eleven reports cannot drift from the rule their SQL implements, and a new report id cannot ship without its sentence |
| DEC-098 | The browser widens an audit `from`/`to` business date to whole Asia/Kolkata days at the transport boundary, and an absent bound is omitted rather than sent empty. | Accepted in Phase 09 | An audit event happened at an instant, so a bare `YYYY-MM-DD` would be read as UTC midnight, which is 05:30 in Kolkata, and would silently drop the early hours of the first day and most of the last. The offset is written literally because India observes no daylight saving. Omitting a bound keeps "no lower bound" distinct from "the lower bound is the empty instant", which is a different query for the API to answer |
| DEC-099 | `audit_event.entity_reference` is `VARCHAR(64)`, widened from `VARCHAR(32)` by migration `20261003120000_audit_entity_reference_width`. | Accepted in Phase 10 | `REQ-AUDIT-002` requires a settings change to be audited, and the settings key `DEFAULT_MONTHLY_CONTRIBUTION_PAISE` is 34 characters, so a 32-character column could not store the entity reference and the audit insert failed while the settings row itself committed (`ISSUE-046`). Matching the column to the widest audited reference in the system removes the class of failure rather than special-casing one key, and expressing it as a reviewed forward migration keeps `prisma/schema.prisma` and the database in agreement with no drift |
| DEC-100 | Browser feature clients pass a path relative to the versioned base (`/audit-events`, `/settings`); the shared API client owns the `/api/v1` prefix. | Accepted in Phase 10 | The API client joins its configured base URL, which already ends in `/api/v1`, with the path it is given, so a feature client that repeats the version produced `/api/v1/api/v1/...` and every request 404'd (`ISSUE-047`). The income and expense features already follow the relative-path rule and work, so Phase 10 aligns the audit and settings clients with them instead of teaching the client to detect a duplicate prefix, which would make the base URL ambiguous |
| DEC-101 | Every settings write obtains a CSRF token through `withCsrf`, exactly like every other state-changing browser write. | Accepted in Phase 10 | `docs/07-SECURITY-RULES.md` requires a CSRF token on state-changing requests, and the two settings mutations omitted it, so every save was refused `403 CSRF_FAILED` and the monthly contribution could not be changed from the interface (`ISSUE-048`). Routing the writes through the same helper as every other mutation keeps one enforcement point and one failure mode rather than a second, weaker path that has to be remembered per feature |
| DEC-102 | Audit-history filter parsing separates vocabulary errors from date-boundary errors: a bad `entityType`/`action` reports `Choose one of ...`, and a malformed `from`/`to` names the offending bound with the `YYYY-MM-DD` message. | Accepted in Phase 10 | `toHistoryFilter` shared one throw for both checks, so an invalid vocabulary value was reported to the Admin as a bad date (`ISSUE-049`), which names the wrong field and misdirects the fix. Keeping the messages distinct costs one small parser and makes the error describe the input that was actually wrong, without changing the endpoint, contract, or status code |

## Phase 11 UI integration decisions

| DEC-103 | The application shell renders one labelled `Primary` navigation landmark that serves as both the desktop sticky sidebar and the mobile drawer, and the collapsed state is persisted in `localStorage` under `hyssop.navigation.sidebar-collapsed`. | Accepted in Phase 11 | `REQ-RESP-002` requires a desktop sidebar and `REQ-RESP-003` requires a collapsible sidebar and a mobile drawer, which could be read as two navigation structures. Rendering two structures would put two `navigation` landmarks with the same accessible name on the page and would make `TEST-RESP-001` unable to name one of them unambiguously; one list reused in two presentations keeps a single source of label order, so a section can never be reachable on desktop but missing on mobile. Persisting the collapse choice is a presentation preference, so `localStorage` is the correct scope rather than the server, and a storage failure is treated as a non-event so a blocked or unavailable store degrades to the default expanded rail instead of breaking the shell. |
| DEC-104 | Unsaved-work protection is one provider mounted inside the route tree, and each form registers through `useUnsavedWork(isDirty)`; navigation blocking uses the data router's `useBlocker`, and non-route confirmations go through `requestConfirmation()`. | Accepted in Phase 11 | `docs/03-UI-UX-RULES.md` and `REQ-RESP-009` require a warning before navigation or sign-out discards unsaved edits, and `react-router-dom` `useBlocker` only works inside a data router. `AppProviders` sits outside `RouterProvider` in `main.tsx`, so the provider has to live in the route tree (`AppLayout`) to obtain that context, and the sign-out control sits in the same shell so it can confirm through `requestConfirmation()` rather than blocking a route change. A per-form boolean keeps each form the owner of its own dirty definition instead of teaching the provider about every field, and correction forms advance a saved baseline on a successful save so a completed correction is not falsely reported as dirty. The alternative of one global beforeunload-only guard would satisfy the browser-close case but not the in-app navigation and sign-out cases the requirements name. |
| DEC-105 | A standalone Documents/Receipts navigation section is intentionally omitted: receipts are attached and managed inside the transaction record, and document and audit reports are reached inside Reports. | Accepted in Phase 11 | `docs/03-UI-UX-RULES.md` forbids `Coming Soon` placeholders and dead navigation entries, and `REQ-RESP-010` forbids a visible control with no working path. A top-level Documents section would have no screen of its own to open, because the storage subsystem is bound to transactions by id and the reports that surface documents live inside the Reports section, so listing it would produce exactly the dead entry the rules prohibit. This is an approved deviation from a literal reading of the navigation inventory, recorded here rather than silently dropped, and the shell comment that references it points at this decision. |

## Phase 12 final QA decisions

| ID | Decision | Status | Reason and impact |
|---|---|---|---|
| DEC-106 | Implement one in-process `RequestRateLimiter` (sliding window) behind a global `RateLimitGuard` for the `mutation`, `search`, `upload`, and `export` categories, configured through validated `RATE_LIMIT_WINDOW_MINUTES` and `{MUTATION,SEARCH,UPLOAD,EXPORT}_RATE_LIMIT_MAX_REQUESTS` keys, and keep the dedicated pre-credential `LoginRateLimiter` separate. | Accepted in Phase 12, mandated security-control gap corrected | `docs/07-SECURITY-RULES.md` already required safe login/upload/search/export/mutation limits and stated they are "required, not optional, and final QA must test their threshold and generic-error behavior"; only the login limiter had been implemented, so Phase 12's adversarial security review found a required control missing rather than a new requirement. The guard enforces an explicit `@RateLimit(category)` where present (upload, search, export), otherwise treats every non-`GET`/`HEAD`/`OPTIONS` method as `mutation`, leaves safe methods unlimited, and opts login/logout out with `@RateLimit('none')` because login already has its own limiter. It returns the documented generic `429 RATE_LIMITED` envelope with a `Retry-After` hint and is registered after `SessionGuard`, so an unauthenticated request is refused `401` rather than misreported as rate-limited. The limiter is in-process, so the limit is per API instance exactly like `DEC-066`, and that shared-store limitation is carried by `ISSUE-022`. Demo defaults are deliberately generous (300 mutation/search, 120 upload/export per minute) so ordinary use is unaffected. Threshold and generic-error behavior are proven at the HTTP layer against real PostgreSQL (`TEST-SEC-001`). |

## Decision protocol

Before changing a decision, update the relevant specification, record the reason and impact here, and confirm that no locked requirement is weakened. Record rejected alternatives when they clarify future work.
