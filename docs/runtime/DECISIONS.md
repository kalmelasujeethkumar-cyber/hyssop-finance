# HYSSOP FINANCE — Decisions

## Document Responsibility

- Owns: accepted technical decisions, `DEC-*` identifiers, reasons, alternatives, and impacts.
- Does not own: current status, open issues, test results, or locked product requirements.
- Referenced by: affected specifications, phase documents, and the traceability matrix.
- Change rule: record a decision only after the owning specification is updated or confirmed; a decision that weakens a locked requirement is a stop-and-ask condition.

Decisions are recorded so that future phases do not rely on conversational memory. A decision that conflicts with a locked requirement must stop and ask the user instead of being recorded as settled.

## Phase 02 database decisions

| ID | Decision | Status | Impact |
|---|---|---|---|
| DEC-054 | Provision the disposable database with a project-local PostgreSQL 16 cluster managed by `scripts/local-postgres.mjs` (loopback-only, non-default port, `trust` authentication, no stored credentials) instead of the Docker/Compose path. | Accepted in Phase 02 | Docker is not installed on the developer machine, so the Compose files stay an unverified alternative (`ISSUE-016`). The local cluster, role separation, and migrations are identical to a container, and no credential is written to the repository. |
| DEC-055 | Own object-level runtime grants in a reviewed forward migration and keep the provisioning script responsible only for instance-level facts (roles, databases, `CONNECT`, schema `USAGE`). | Accepted in Phase 02 | `prisma migrate reset`, `migrate dev`, and a recreated database silently discard grants issued outside migration history. That previously left `hyssop_finance_dev` readable by nobody except the migrator while every migration still reported success, so the development application could not read its own data. Owning the grants in `20260926140000_runtime_role_grants` also sets default privileges so later migrations do not break the runtime role, and it keeps the append-only audit revoke with the schema it protects. |
| DEC-056 | Persist an idempotent command and its stored response in one transaction (`IdempotencyRecordRepository.runOnce`) instead of a begin/complete/abandon claim lifecycle. | Accepted in Phase 02 | A claim row with no stored response can no longer leave a permanent `409`-style dead key, a failed command can never leave a claimed key behind, and a concurrent loser replays the winner's stored response from the unique conflict. The `response_status` check now only accepts real HTTP statuses (`100`–`599`). |
| DEC-057 | Bind business-date query parameters as `formatBusinessDate(value)::date` rather than sending a bare timestamp. | Accepted in Phase 02 | Reconciliation stops depending on the session `TimeZone`; the same period range returns the same rows regardless of the server or connection timezone. |
| DEC-058 | Seed document *metadata* only, with no physical object, while transaction, member, period, category, and settings fixtures are seeded. | Accepted in Phase 02 | The seed never claims a stored file that does not exist, and no database column or seed path implies raw file storage. Phases 07 and 12 own the storage adapter and the durable storage decision. |
| DEC-059 | Derive the test database URL from the development URLs when no explicit test URL is supplied, and refuse any database name that does not end in `_test`. | Accepted in Phase 02 | `npm run test:db` works from the repository root with no manual environment setup, while the destructive test harness can only ever target a disposable `_test` database. |
| DEC-060 | Declare the `member_id` and `category_id` transaction indexes as full indexes on the documented column order instead of partial indexes on active rows. | Accepted in Phase 02, deviation recorded | Prisma 6.19 cannot express a partial index in the datamodel; adding the `WHERE status = 'ACTIVE'` predicate only in the migration makes `prisma migrate diff` report permanent drift on every run. The documented leading columns and query support are unchanged, so the deviation costs index size and nothing else. Recorded as `ISSUE-013` so a reviewer can require strict partial indexes by accepting drift or changing the migration strategy. |
| DEC-061 | Keep the Prisma 6 `package.json#prisma` configuration and treat the Prisma 7 `prisma.config.ts` migration as separate future work. | Accepted in Phase 02 | The current toolchain builds, migrates, tests, and seeds cleanly; moving configuration formats mid-phase would add an unrelated failure mode to the database gate. The deprecation warning is recorded as `ISSUE-015`. |
| DEC-062 | Own migration-drift verification in `scripts/migration-drift.mjs` (`npm run db:drift`): compare migration history against the datamodel using a disposable `_shadow` database that the script creates and always drops, then compare the live development database with the read-only `--from-url` check. Never point `--shadow-database-url` at a database that holds data. | Accepted in Phase 03 preflight | `prisma migrate diff` resets its shadow database before use, so a shadow URL pointed at a live database silently destroys it (`ISSUE-017`). A script-owned throwaway database removes the possibility of that mistake, the `_shadow` name guard turns a mistyped variable into an immediate refusal instead of data loss, and the read-only live comparison proves the real development database still matches the schema. Every later phase that adds a migration can run one safe command. |
| DEC-063 | Configure explicit interactive-transaction waits on the shared Prisma client (`maxWait` 15 s, `timeout` 30 s) instead of Prisma's 2 s / 5 s defaults. | Accepted in Phase 03 preflight | Reference allocation is serialized per scope by the `id_sequence` row lock, so concurrent writers queue by design. With the defaults the last writer in a documented burst fails with `Unable to start a transaction in the given time`, which is a client-side acquisition timeout, not a uniqueness or locking failure, and would surface to the API as a spurious server error (`ISSUE-018`). The waits stay bounded, so a genuinely stuck transaction still fails instead of hanging, and the no-duplicate guarantee is still enforced by the row lock and the unique constraint rather than by any timeout. |

## Decision protocol

Before changing a decision, update the relevant specification, record the reason and impact here, and confirm that no locked requirement is weakened. Record rejected alternatives when they clarify future work.
